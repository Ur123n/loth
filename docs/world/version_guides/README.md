## 3. Codex每次开工顺序

1. 读项目AGENTS、最新WORKLOG、本指南和目标地图当前加载链。核对磁盘、Git状态（若无Git则记录）、正在运行的Godot实例及入口。
2. 选择任务类型：`surface`材质、`layout`布局、`interaction`玩法、`integration`接入；写清目标地图和可变/不可变项。
3. 用[任务模板](version_task.template.json)创建本次任务文件，填新revision_id（例如iserra_surface_20261005_r01），不得把模板的空值当默认许可。
4. 记录实际修改集合与共享依赖。备份原文件、资源引用和哈希；候选先在独立目录构建。
5. 完成一个最小区段：灰盒试玩 → 分层材质 → Godot实际画面 → 逻辑不变量比对，再扩展。
6. 完成针对性与相关回归，提供可运行候选和固定视点对比。已授权的常规工作持续执行，不反复询问同一许可。
7. 按任务授权切换活动版本；替换后重新加载实际入口并复验，再记发布/回退记录。

## 4. 目录与版本记录

建议约定（执行任务时创建，当前不代表已存在）：

```text
C:/美术素材制作/working/<revision_id>/       原图、提示词、参考、来源哈希
C:/游戏/dev/map_versions/<revision_id>/   候选场景、绑定脚本、QA、WORKLOG
C:/游戏/assets/map_versions/<revision_id>/ 需保留的运行材质依赖
C:/游戏/maps/leyton/archive/<revision_id>_before/ 精确备份，带.gdignore
```

新运行资源采用唯一版本路径，避免覆盖其他地图正在引用的共享材质。建筑逻辑id保持或变更必须明确：材质目录不额外注册一份相同id建筑；如果创建可独立扫描的完整建筑包，使用唯一id并更新引用。备份不能留在活动建筑扫描目录中充当另一座建筑。

记录分开：`source_revision`、`candidate_revision`、`active_revision`、确认范围、变更文件清单、修改前/后哈希、验证时间和日志。日期最大或文件最新不等于正在加载。

## 5. 共享资源与候选隔离

替换共享文件会影响所有引用者。只隔离地图场景、却覆盖共享PNG/TileSet/脚本，仍会改变现行地图。候选依赖也必须隔离并显式引用；发布时只切换经过验证的引用/文件集合。

图层alpha来自明确的几何稿；已有视觉可重做，碰撞仍来自逻辑数据。不要让Shader fallback大面积填色掩盖缺图。校验完整层和实际遮挡分区的UV对应、边缘、脚点及真实画面。

## 6. 验证与发布规则

- 纯材质更新：相关逻辑字段/掩码、出口、出生、门禁、墙梯、角色通行结果应不变；代码/材质本身的哈希允许按清单变化。
- 布局或玩法更新：先列允许变化的字段及新验收目标，其余维持。不能把所有变化都称作“美术替换”。
- 测试依据当前断言和输出，不能复用旧的通过次数。测试失败先区分既有问题和本次回归，记录证据；不能删除失败断言或改哈希让测试表面通过。
- 实际图形验证必须打开目标地图；headless成功不证明屋顶、材质或遮挡正确。没有图形验证时写`file-level verification only`。
- 来源收据、程序测试、用户美术确认、部署确认分别记录；某一项通过不冒充其余项。

**替换步骤：**核对活动文件仍与备份前哈希相同 → 保存候选完整依赖和通过证据 → 关闭/刷新相应实例 → 暂存并校验JSON/TSCN资源 → 原子替换清单内文件 → Godot导入 → 从真实BAT/主场景加载 → 重走关键路线 → 记录active_revision。

不假定多文件复制具有事务性。每写一个文件记清单；中途失败停止，按本次清单恢复已替换项，再验证旧版本。若发现并行修改，保留双方版本并核对差异，不直接用备份覆盖。

**回退步骤：**确认要回退的revision及精确目标 → 核对目标属于工程范围 → 恢复该版本保存的原文件/引用 → 导入并重启目标入口 → 验证旧哈希与关键路线 → 记回退原因。新增加但已无引用的候选先保留，删除与备份清理独立处理，不递归删除整个maps/assets目录。

## 7. 何时问用户

遇到以下未在当前任务授权的决定时提问，并继续不依赖答案的工作：改变占地/门/道路/出口；开放原不可进入室内；调整故事功能或世界观；改变主要建筑身份/轮廓风格；将样段扩展到多个未指定城区；移除已有功能；目标版本存在冲突且无法从现场判断。

问题须附实际差异与建议，例如“保持48×58占地，仅更换表面，还是同时开放教堂室内？”不要再次询问已允许的修道院贴图更换。实际实施中先做能审阅的小样/差异图，再请求超出范围的选择。

## 8. 验收交付格式

给用户：修改范围、运行入口、前后对照、通过检查、剩余问题、当前活动版本及回退点。给后续Codex：任务文件、依赖/哈希清单、完整提示词、日志、截图与WORKLOG。不得只说“生成完成”。
