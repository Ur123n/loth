

Project README — 六边形战棋卡牌 RPG

1. 项目概述

本项目是一款以角色塑造、探索、剧情和六边形战棋卡牌战斗为核心的单人 RPG。

游戏由以下几个主要部分组成：

大世界探索

城镇与地点

NPC 与关系

剧情与对话

任务系统

四人固定队伍

六边形战棋战斗

卡牌战斗系统

角色成长

道途系统

装备系统

敌人与 Boss

存档系统

核心战斗体验：

四人固定小队 + 六边形空间战斗 + 独立角色卡组 + 独立资源 + 玩家自主角色成长。

核心 RPG 体验：

玩家不是选择一个固定职业，而是在剧情、战斗、装备和卡牌选择中逐渐塑造角色。

2. 总体开发原则

2.1 模块化优先

项目必须采用模块化架构。

任何大型系统都必须拥有明确的：

数据

逻辑

UI

资源

文档

模块之间通过明确接口通信。

禁止让一个系统直接依赖另一个系统的内部实现。

2.2 系统与内容分离

这是本项目最重要的架构原则之一。

系统

负责：

“游戏规则如何运行。”

例如：

CardSystem

BattleSystem

EffectSystem

CharacterSystem

QuestSystem

内容

负责：

“游戏中具体存在什么东西。”

例如：

鲍德温

某张卡牌

某件装备

某个 NPC

某个任务

某张地图

新增游戏内容时，原则上应该通过数据资源完成，而不是修改核心系统。

4. Core 与 Content

core/

存放游戏规则和通用系统。

例如：

core/card/ 

负责：

卡牌数据结构

抽牌

弃牌

费用

荷载

卡牌执行

但是不应该知道：

“鲍德温的圣光斩是什么。”

content/

存放具体游戏内容。

例如：

content/cards/baldwin/holy_strike.tres 

描述：

名称

费用

荷载

类型

效果

图标

描述

这样新增一张卡牌通常不需要修改 core/card/。

5. Godot 数据驱动原则

Godot 项目优先使用 Resource / .tres / .res 等数据资源描述游戏内容。

推荐：

CardData CharacterData EquipmentData EnemyData QuestData NPCData DialogueData MapData EncounterData 

代码负责规则。

Resource 负责数据。

例如：

CardData ├── Name ├── Description ├── Type ├── Cost ├── Load ├── Range ├── TargetType └── Effects 

禁止把大量游戏内容硬编码到 .gd 文件中。

7. RPG系统之间的关系

推荐依赖方向：

World ↓ Quest / Dialogue ↓ Character / Progression ↓ Battle ↓ Card / Effect 

但底层系统不能反向依赖上层系统。

例如：

CardSystem 

不能直接调用：

WorldManager 

如果战斗结束需要改变剧情，应返回：

BattleResult 

由上层系统处理。

8. 事件驱动

跨模块通信优先使用：

Signal

Event

Result Data

而不是直接访问另一个模块的内部变量。

例如：

战斗结束：

BattleSystem ↓ BattleResult ↓ GameManager ↓ QuestSystem ↓ StorySystem 

而不是：

BattleManager 直接修改 QuestManager.quest_data 

9. UI 与游戏逻辑分离

UI 不负责决定游戏规则。

例如：

卡牌 UI：

CardUI 

负责：

显示卡牌

显示费用

显示荷载

接收点击

真正使用卡牌：

CardSystem 

负责。

同理：

角色面板只显示属性。

属性修改必须由：

CharacterSystem 

处理。

10. 模块文档规则

每个大型模块都应该拥有自己的：

README.md rules.md architecture.md 

README

回答：

这个模块是什么？

rules

回答：

这个模块遵守什么游戏规则？

architecture

回答：

代码是如何实现这些规则的？

11. Codex 工作准则

Codex 每次处理任务时：

第一步：识别模块

确定任务属于：

Battle Card Character World Quest Dialogue Equipment UI Save 

之一或多个模块。

第二步：读取局部文档

优先读取对应：

docs/<module>/ 

而不是扫描整个项目。

第三步：检查依赖

只读取当前模块直接依赖的模块。

第四步：修改

只修改完成任务所需要的文件。

第五步：测试

执行对应模块测试。

第六步：更新文档

如果修改改变了系统行为：

同步更新对应 rules.md 或 architecture.md。

12. 禁止行为

Codex 不得未经明确要求：

重构整个项目

修改无关模块

删除现有系统

修改核心游戏规则

将数据硬编码进系统

创建重复功能

为单张卡牌复制一套新的卡牌系统

为单个 NPC 创建独立任务系统

为单个角色复制一套成长系统

如果现有架构无法满足需求：

先说明问题和建议方案，再进行大规模重构。

13. 修改现有系统的规则

任何涉及核心系统的修改必须优先保证：

现有功能不被破坏 

修改后必须测试：

当前战斗是否仍然能够完整进行

已有卡牌是否正常

已有角色是否正常

已有存档是否能够读取

其他模块是否受到影响

15. 开发阶段

项目开发遵循：

核心系统 ↓ 垂直切片 ↓ 内容扩展 ↓ 世界系统 ↓ 剧情系统 ↓ 美术与表现 ↓ 完整内容生产 ↓ 优化与测试 

不要在核心系统尚未稳定时大量生产内容。

16. 内容生产原则

新增内容优先使用已有系统。

例如新增卡牌：

优先：

已有 Effect 组合 

只有现有 Effect 无法表达时，才新增 Effect。

同理：

新增任务：

优先使用已有：

条件

Flag

奖励

对话节点

而不是为一个任务创造新的任务机制。

17. 项目规模控制

本项目预计为大型个人 RPG。

因此必须优先考虑：

可扩展性

可维护性

数据驱动

模块隔离

自动测试

文档同步

不要为了快速实现一个功能而破坏长期架构。

个人开发者的主要风险不是开发速度不足，而是：

项目规模增长后无法维护。

因此优先保证：

“未来可以继续添加内容，而不是现在最快完成内容。”

18. 当前核心目标

项目最终应形成以下循环：

探索世界 ↓ 发现地点 / NPC / 任务 ↓ 剧情与选择 ↓ 获得资源 / 装备 / 卡牌 / 成长机会 ↓ 培养四人队伍 ↓ 进入六边形战斗 ↓ 通过战斗获得新的成长 ↓ 影响世界与剧情 ↓ 继续探索 

最终目标不是制作一个拥有大量独立系统的游戏，而是让这些系统形成一个统一的 RPG 循环：

探索塑造角色，角色影响战斗，战斗推动成长，成长改变玩家面对世界的方式，而玩家的选择最终反过来改变世界。

19. Codex 快速参考

当收到开发任务时，首先判断：

这是哪个模块？ ↓ 读取该模块 docs ↓ 检查直接依赖 ↓ 修改最少必要文件 ↓ 运行相关测试 ↓ 确认没有破坏其他模块 ↓ 更新文档 

不要为了完成局部任务而读取和修改整个项目。

不要把具体游戏内容写进核心系统。

不要让模块互相直接侵入内部实现。

优先扩展已有系统，而不是创建平行系统。

当规则发生变化时，先更新规则文档，再修改代码。

建议你再配一个 AGENTS.md

README 是给人看的项目总览，而 AGENTS.md 才应该是给 Codex 的执行规范。

两者不要完全重复：

README.md ↓ 项目是什么、有哪些系统、项目怎么组织 AGENTS.md ↓ Codex具体应该怎么工作、哪些事情不能做、修改代码的流程是什么 docs/ ↓ 每个模块具体怎么实现 

这样你的项目规模即使以后扩大到几百个甚至上千个文件，Codex也不需要每次从头理解整个 RPG，而是可以沿着：

AGENTS.md → 模块文档 → 直接依赖 → 具体代码

这条路径工作。
